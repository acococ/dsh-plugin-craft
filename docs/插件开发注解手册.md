## 零、先搞懂「宿主」和三个依赖字段

**「宿主」（host）= 运行你这个插件的那个大程序，也就是 DSH。**

打个比方：

```
DSH        = 一座商场
Cordis     = 商场的电路 / 插座标准
你的插件    = 用这个标准造出来的一件电器
```

电器得插进商场的插座才通电 —— 你的插件必须依赖 DSH 底下那套 Cordis 框架。
这就是各处注释里说的「宿主框架」。

**三个依赖字段的区别，一句话就是：谁装、装给谁、装几份**

| 字段               | 含义           | 装几份       | 举例     |
| ------------------ | -------------- | ------------ | -------- |
| `dependencies`     | 随包装给用户   | 每人一份     | `tsdown` |
| `devDependencies`  | 只装开发者电脑 | 每人一份     | `vitest` |
| `peerDependencies` | 你必须已经有   | **全场一份** | `cordis` |

**为什么 cordis 一定要写 `peerDependencies`？**

宿主自己已经有一份 cordis。如果写进 `dependencies`，pnpm 会在你的
`node_modules` 里**再装一份新的**。于是变成「两份 cordis」：

- 你的插件拿着**新** cordis 的 `ctx` 去注册工具
- 宿主拿着**老** cordis 的 `ctx` 去找工具
- 两边互不相认 → 你注册的工具宿主永远看不见

表现就是「工具明明写了却不出现」，而且没有任何报错，很难查。
写成 `peerDependencies` 后 pnpm 不给你装第二份，全场只有一份。

**里面填的是版本范围，不是某个具体版本**

写法对照（下面都是 semver 实测结果）：

| 写法                  | 含义                         | 实测                       |
| --------------------- | ---------------------------- | -------------------------- |
| `^4.0.2`              | 兼容范围，4.x 随便用         | 接受 4.99.99，拒绝 5.0.0   |
| `^22.19.0`            | 22.19.0 ~ 22.x               | 接受 22.20.1，拒绝 22.18.0 |
| `>=0.1.2-rc.1 <0.2.0` | 大于等于前者 **且** 小于后者 | —                          |
| `A \|\| B`            | 满足任意一段即可             | —                          |

`dsh-tools` 那串长范围逐字读就是「满足以下任意一段」：

```
>= 0.1.2-rc.1 且 < 0.2.0
>= 0.1.5-alpha.1 且 < 0.2.0
>= 0.1.6-0 且 < 0.2.0
>= 0.1.7-0 且 < 0.2.0
```

实测它实际等价于 `>= 0.1.2-rc.1 且 < 0.2.0`，后面几段是冗余的。
**那为什么不简化？**

1. semver 默认规矩是**预发布版不算数**。实测只写 `^0.1.2` 的话，
   `0.1.7-rc.2` 会被**拒绝**（带 `-rc` / `-alpha` 的是预发布版）。
   而官方恰恰大量发预发布版（你环境里就装着 `0.1.7-rc.2`），
   所以必须显式写出带预发布号的下限才能纳进来。
2. 多写的那几段相当于一份「已验证白名单」记录。

这段范围**写死在 `check.ts` 里**，自己不能改，照抄。

**「每个版本功能不一样吗？」** 是的，版本不同功能确实不同。
但写版本范围的意思是：我只用了「从 0.1.2 到 0.2.0 之间一直没变」的稳定接口，
所以中间任何小版本都能用。到了 0.2.0 属于大版本更迭，接口可能变了，
所以卡一个 `<0.2.0`。

## 一、package.json 字段分类

分类图例：

| 标记       | 含义                  | 违反后果               |
| ---------- | --------------------- | ---------------------- |
| **[强制]** | DSH 官方校验器判 FAIL | 过不了门禁，必须改对   |
| **[约定]** | 校验器判 WARN         | 能跑，但官方建议这么写 |
| **[固定]** | npm/Node 标准字段     | 名字不能改，值一般可调 |
| **[自选]** | 本项目自己的取值      | 随便改，不影响框架行为 |

### 强制字段（不改就 FAIL）

| 字段               | 硬性要求                                       |
| ------------------ | ---------------------------------------------- |
| `main`             | 必须有，且指向**已构建**产物                   |
| `engines.node`     | 必须同时覆盖 22 和 24                          |
| `peerDependencies` | 每个 `@deepseek-ai/*` 都要声明，范围须精确一致 |
| `files`            | 须含：层文件 + `main` + `lib`/`dist`           |
| `dsh.bundle.patch` | 指向的层文件必须存在                           |

peerDependencies 的版本范围是**写死在 check.ts 里**的，不能自己发挥：

```
@deepseek-ai/cordis       →  ^4.0.2
@deepseek-ai/schemastery  →  ^3.18.2
@deepseek-ai/dsh-*        →  >=0.1.2-rc.1 <0.2.0 || >=0.1.5-alpha.1 <0.2.0
                            || >=0.1.6-0 <0.2.0 || >=0.1.7-0 <0.2.0
```

> 为什么 `dsh-*` 的范围这么长：要覆盖官方那批带 `rc` / `alpha` 的预发布版本。
> 范围太窄，正式版发出来之前就装不上。

**关于 `engines` 的子字段**：只有 `node` 一个。
校验器的类型定义就是 `engines?: { node?: string }`，只读这一个键
（`check.ts` 的 `checkManifestEngines()`），写别的键既不报错也不生效。
官方脚手架模板和 `dsh-plugin-guide` 自己的 `package.json` 也都只有 `node`。

> npm 层面 `engines` 官方还支持 `npm` 键（声明兼容的 npm 版本），
> 但 DSH 校验器完全不看它，本生态约定就只写 `node`。
>
> 另外：旧版 CHANGELOG 里出现过 `engines.dsh`（声明宿主版本范围），
> **当前已不存在，校验器也不检查它**。看到旧文档提到别照抄。

### 约定字段（WARN）

| 字段             | 官方建议                                       |
| ---------------- | ---------------------------------------------- |
| `packageManager` | `pnpm@11.7.0`                                  |
| README           | 五语：`README.md` 缺了 FAIL，其余四种缺了 WARN |

> `files` 同时出现在两张表里，因为它有**两级要求**：
> 硬性层面必须含层文件 + `main` + 产物目录（缺了 FAIL）；
> 建议层面是别忘了它同时是你控制包体积的唯一手段。

### DSH 专有字段

`dsh` 块不是 npm 标准，别的包管理器会直接忽略。**整个 DSH 生态靠它区分两种插件**：

```jsonc
// bundle 插件：随包分发组合层，改配置要重启
"dsh": { "bundle": { "patch": "./cordis.patch.yml" } }

// profile：可运行组合，由 dsh plugin 命令自动维护，手写不允许
"dsh": { "profile": { "bundles": ["@deepseek-ai/dsh-base", "my-bundle"] } }
```

不写 `dsh.bundle` 的包仍能装，但只作为普通依赖，**宿主不会激活任何层**（装的时候会打印警告）。

## 二、cordis.patch.yml 层文件

### 语法铁律：每个顶层条目都必须是「动词 + 行列表」

```yaml
- insert:              # ← 动词，值的类型必须是列表
    - id: my-plugin    # ← 行
      name: my-plugin
      config: {...}
```

**踩坑警告**：裸写一个 `- id: xxx / name: xxx / config: {...}` 是**不合法**的。
加载器会把没有动词的裸行当成「按 id 覆盖一个**已存在**的行」，
而你要插入的是新行 → 找不到同名行 → 直接丢弃并打印：

```
dsh: [<bundle名>] patch: entry "<id>" not found
```

这个错误**不致命，宿主照常启动**，所以「插件根本没加载」这件事极难发现。
症状是：预设/persona 加载了，但它叫模型去调的工具全部不存在。

> **本项目实例**：`dsh-plugin-craft` 0.3.4 就踩了这个坑 ——
> `dsh-plugin-craft` 宿主行从未加载，三个 `craft.*` 工具从未注册，
> 而 `preset-craft` 预设却加载了，于是 persona 一直在叫模型调不存在的工具。
> 直到写这份文档时用 `dsh --profile web --dump-config` 才抓出来。
> 源码已修复，但已发布的 `dsh-plugin-craft-0.3.4.tgz` 里仍是坏的，
> 重新 `pnpm pack` 才会带上修复。

### 分层顺序（后层覆盖前层）

1. profile 的 `dsh.profile.bundles` 列表顺序（`@deepseek-ai/dsh-base` 永远第一层）
2. profile 自己的 `cordis.patch.yml`
3. 机器级 `$DSH_HOME/cordis.patch.yml`
4. 命令行 `--patch <path>`

**覆盖是按 id 整行替换 config，不做深合并** —— 覆盖方必须重述该行需要的全部键。

### 验证命令

```bash
dsh --profile <name> --dump-config    # 看 patch 行是否真的生效
```

## 三、源码红线（校验器会扫）

| 红线                  | 说明                                    |
| --------------------- | --------------------------------------- |
| 配置必须 Schema 化    | 不能是普通对象                          |
| 注册即 effect         | 一律走 `ctx.effect()` / `register()`    |
| 禁止手动收尾          | 出现 `removeListener` / `.off` 会被标记 |
| waterfall 调 `next()` | 不调 = 故意短路                         |
| `apply` 不能 async    | 首个 `await` 后不得再注册               |
| 模型可见 ⟺ 已记录     | 新增可见输入须配会话事件                |
| 工具只返回规范值      | 人话放 `output.render`                  |
| presenter 是纯函数    | 禁 I/O / 时钟 / 随机                    |

## 四、新插件空白模板

复制下面三块，按注释填空即可。改完记得跑第五节的自查清单。

### package.json

```jsonc
{
  // 三处必须一致：这里、src/index.ts 的 name、cordis.patch.yml 的 name
  "name": "my-dsh-plugin",
  "version": "0.1.0",
  "description": "一句话说明这个插件做什么",
  "type": "module",

  // [强制] 指向构建产物，不能指向 src/
  "main": "lib/index.mjs",
  "types": "lib/index.d.mts",

  "exports": {
    ".": { "types": "./lib/index.d.mts", "default": "./lib/index.mjs" },
    "./package.json": "./package.json"
  },

  // [强制] 必须含：层文件 + main 入口 + 构建产物目录
  "files": ["lib", "cordis.patch.yml", "README.md", "LICENSE"],

  "scripts": {
    "build": "tsdown",
    "typecheck": "tsc --noEmit",
    "test": "vitest run",
    // 从 git 安装时需要先构建；从 npm/tarball 装则可去掉
    "prepare": "npm run build"
  },

  "dependencies": { "tsdown": "^0.22.14" },

  // [强制] 版本范围照抄，不要自己发挥
  "peerDependencies": {
    "@deepseek-ai/cordis": "^4.0.2",
    "@deepseek-ai/dsh-tools": ">=0.1.2-rc.1 <0.2.0 || >=0.1.5-alpha.1 <0.2.0 || >=0.1.6-0 <0.2.0 || >=0.1.7-0 <0.2.0",
    "@deepseek-ai/schemastery": "^3.18.2"
  },
  "devDependencies": {
    "@deepseek-ai/cordis": "^4.0.2",
    "@deepseek-ai/dsh-tools": ">=0.1.2-rc.1 <0.2.0 || >=0.1.5-alpha.1 <0.2.0 || >=0.1.6-0 <0.2.0 || >=0.1.7-0 <0.2.0",
    "@deepseek-ai/schemastery": "^3.18.2",
    "@types/node": "^22.20.1",
    "vitest": "^3.2.7"
  },

  // [强制] 宿主专有字段，没有它宿主不会激活任何层
  "dsh": {
    "bundle": { "patch": "./cordis.patch.yml" },
    "manifestVersion": 1
  },

  // [强制] 必须同时覆盖 Node 22 和 24
  "engines": { "node": "^22.19.0 || >=24.0.0" },
  "packageManager": "pnpm@11.7.0",
  "license": "Apache-2.0"
}
```

### cordis.patch.yml

```yaml
# 注意 `- insert:` 这个动词不能省！
# 裸行会被当成「覆盖已存在的行」，找不到就静默丢弃。
- insert:
    - id: my-plugin
      name: my-dsh-plugin
      config:
        # 这里放你 Config schema 里的字段
        myOption: 1
```

### src/index.ts 骨架

```ts
import Schema from '@deepseek-ai/schemastery'
import type { Context } from '@deepseek-ai/cordis'
import { defineTool } from '@deepseek-ai/dsh-tools'

// [强制] 配置必须 Schema 化，不能是普通对象
export interface Config { myOption: number }
export const Config: Schema<Config> = Schema.object({
  myOption: Schema.number().default(1).min(1).description('说明文字会出现在 --dump-config 输出里'),
})

// 三处一致
export const name = 'my-dsh-plugin'

// 声明依赖的服务；服务消失会自动卸载，回来自动重载
export const inject = ['tools'] as const

// 让别的插件能拿到 ctx.myService 的完整类型；编译期抹除，运行时无副作用
declare module '@deepseek-ai/cordis' {
  interface Context { myService: MyService }
}

export function apply(ctx: Context, config: Config): void {
  // [红线] 一切贡献走 ctx.effect()，不要自己写 removeListener/clearInterval
  ctx.effect(() => ctx.provide('myService', new MyService(config)), 'my-plugin: service')

  ctx.tools.register(defineTool({
    name: 'my.do_thing',
    description: '给模型看的：什么时候该调这个工具',
    parameters: { /* ... */ },
    output: {
      schema: { type: 'object', additionalProperties: false, properties: {} },
      // [红线] presenter 是纯函数，禁 I/O / 时钟 / 随机
      render: (_args, value) => [{ type: 'text', text: `结果：${JSON.stringify(value)}` }],
    },
    // [红线] execute 只能返回 output.schema 里声明的规范 JSON
    async execute(args) { return {} },
  }))
}
```

## 五、提交前自查清单

```bash
pnpm typecheck                    # 类型检查
pnpm test                         # 跑测试
pnpm build                        # 构建（main 必须指向构建产物，没构建会 WARN）

# 官方门禁：静态检查 + 工程红线
node dsh-plugin-guide/dist/dsh-plugin-dev.js check --strict

# 打包 → 装进干净的临时 DSH_HOME → 启动 → 卸载，做安装冒烟
node dsh-plugin-guide/dist/dsh-plugin-dev.js verify

# 最后确认 patch 行真的被加载了（这一步能抓出「裸行被静默丢弃」）
dsh --profile <name> --dump-config | grep <你的插件名>
```

> `check` 查的是**包本身合不合规**；`verify` 查的是**装上去能不能跑**。
> 两者互补，光跑 `check` 抓不到本文第二节那个 `- insert:` 的坑 ——
> `check` 能抓到，但 `dump-config` 是最后一道肉眼确认，建议都跑。
